A self-hosted iMessage API that runs on your Mac.

Blue Bubble Club is a small menu bar app with an embedded HTTP API. It works with your signed-in Messages session to send, reply, react and observe without a separate server, cloud relay or UI automation.

How it works

One local app. No server stack.

BBC runs in the macOS login that is signed into Messages. A single Swift app hosts the API, manages keys and receipts, and talks to its own embedded native bridge.

  1. 01

    Your client

    A bot, script or service sends HTTP with a Bearer key and an Idempotency-Key UUID.

    curl · any HTTP client · Swift SDK

  2. 02

    Blue Bubble Club

    A menu bar app with an embedded API on port 7861 by default. It checks the key and client address and records each operation so a retry returns the saved receipt.

    Keys · access rules · receipts · logs

  3. 03

    Messages on your Mac

    Sends go through your signed-in account. History and webhooks come from the local Messages database.

    Your account · your hardware

Capabilities

Enable only what you need.

Features are grouped by the access and host setup they require. Start read-only and add more later.

Observe

Read-only keyFull Disk Access

  • Message history with incremental cursors
  • Search by text, conversation and date
  • Webhooks for incoming messages and observed updates
  • Attachment downloads, including ranged reads
  • Local media processing, with optional on-device transcription

Send

Full-access key+ Messages Automation

  • Text messages over iMessage, with SMS fallback disabled
  • Photos, video and audio from uploaded media
  • Scheduled sends you can update and cancel
  • Operation receipts that prevent duplicate sends

Native

Full-access key+ native messaging setup

  • Threaded replies and Tapbacks, including custom emoji
  • Typing indicators and mark read
  • Rich links with native previews
  • Groups: create, rename, set photo, add, remove, leave
  • Edit, unsend and multipart messages with effects
  • iMessage availability checks

Replies, Tapbacks, read and typing currently target direct chats. Native capabilities vary with macOS, and passing tests do not establish live compatibility on your host. GET /v1/status reports what is available. Read the capability limits.

API

Plain HTTP and JSON, with explicit receipts.

Every route requires a Bearer key. Every mutation requires an Idempotency-Key UUID that you save before dispatch.

Same UUID and body
Returns the saved receipt. Nothing is sent twice.
Same UUID, changed body
Rejected with HTTP 409.
Lost response
Fetch GET /v1/operations/<uuid> and reconcile. Never resend under a new UUID.

Boundaries

Explicit about access and failure.

BBC is designed to fail visibly rather than guess. These are design rules in the codebase, not promises about third-party behaviour.

  • Local by default

    New keys accept loopback connections only. Network access, IP and CIDR allowlists, and read-only or full access are set per key. Forwarded headers never grant access.

  • Keys you can revoke

    Secrets are shown once and stored only as hashes. Rotate or revoke a key in the app; the API cannot create keys.

  • No UI automation

    BBC never clicks, types into the composer or takes over the mouse or keyboard. Unavailable native features fail instead of falling back to the UI.

  • No automatic retries

    An uncertain mutation stays uncertain until you reconcile it. BBC does not dispatch it again on its own.

Native features reduce host protections

Replies, Tapbacks, typing, groups and the other native features currently require you to disable SIP and system library validation yourself. These changes affect every user on that macOS installation. BBC reports the requirement but never changes these settings. Read-only access and ordinary sends work without them.

Get started

From clone to first request.

You need a Mac on macOS 26 or later, Xcode 27.2+ and an Apple Development signing identity. The setup guide has the full steps.

  1. Build and sign

    Clone the repository and run ./script/build_and_run.sh. It builds, packages and signs the app with your identity.

  2. Grant permissions

    Use the Setup checklist to grant Full Disk Access, plus Messages Automation if you want to send. A floating helper sits next to System Settings.

  3. Create a key

    In API Keys, create a named key. New keys are read-only and local-only; choose Full access for sending.

  4. Start the API

    Select Start API, then call GET /v1/status to confirm your key’s access and the available methods.
